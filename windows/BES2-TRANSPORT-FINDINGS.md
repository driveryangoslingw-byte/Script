# Bosch BES2 Intuvia: исправление первого чтения, 23 октября 2026

## Результат

**VERIFIED ON THIS BIKE:** Windows открыл HID `108C:0155`, IN/OUT по 65 байт. После исправления получен положительный BUI ReadDataByIdentifier ответ `62 02 20 05 09 02 00`, версия ПО Intuvia **5.9.2.0**. Независимый контрольный скрипт и исправленный C# runner воспроизвели чтение в отдельных сеансах. Это результат чтения BUI, а не доказательство доступа к мотору или батарее.

## Найденная причина 00 FF

Старая программа отправляла:

```
02 00 07 00 FF FF 0B 00 00 00 3A 04 03 22 02 20
```

Корректный первый запрос, с нулями до 64 байт:

```
02 00 00 00 FF FF 0B 00 00 3A 04 03 22 02 20
```

**DOCUMENTED BY BINARY ANALYSIS + VERIFIED ON THIS BIKE:**

1. Байт 2 — sequence SWA. Новый handshake обнуляет ожидаемый sequence. Фиксированное `07` в старом примере означало номер пакета 7, а не постоянную часть заголовка.
2. CAN-запись начинается с байта 8 и занимает 11 байт. CID находится в байтах 8–9. Старая реализация добавляла лишний ноль и помещала младший байт CID в позицию 10.
3. В найденной прошивке несовпадение sequence переводит обработчик в ветку `00 FF`, очищающую handshake/mode. Поэтому быстрый ответ не был UDS NRC и не устанавливал причину неисправности двигателя.

## Доказательства из публичной прошивки

Исследован [BUI255 firmware 5.9.2.0, commit 50af4c09](https://github.com/vxaa600/bosch-bui255-firmware/tree/50af4c09fef62beb16809ddc2019e96f9ea9be40), файл `stm32.bin`, 262144 байта. SHA256 `fbcb231486d98d8d05e33f67fc07003f9d0366a543c7dc99728e82f42f3ad0a6`.

| Адрес Thumb-кода | Проверенное поведение |
|---|---|
| `08021604` | Обнуляет состояние SWA после handshake |
| `0802169C..080216A8` | Сравнивает packet[2] с ожидаемым sequence |
| `080213C8..080213EE` | Сбрасывает состояние, формирует `00 FF` |
| `08021300` | Возвращает запись по адресу packet + 8 + 11 * index |
| `0802B896..0802B8A6` | Опознаёт локальный BUI CID `003A` |
| `080216CC..08021750` | Формирует специальный исходящий ответ BUI |

Исходные Thumb-инструкции выполнены офлайн в Unicorn. USB-отправка и CAN-доставка заменены наблюдателями. Старый пакет дал `00 FF` без доставки CAN. Исправленный сохранил режим A, увеличил ожидаемый sequence до 1 и передал ровно `00 3A 04 03 22 02 20 00 00 00 00`. Отдельно проверены оба значения обычного прикладного gate; на физическом устройстве этот gate не изменялся. Прошивка велосипеда не читалась и не записывалась; использовался публичный дамп.

## Ответ и границы декодирования

Значимая часть полученного USB64 отчёта:

```
02 00 00 00 08 98 02 01 00 3D 08 07 62 02 20 05 09 02 00
```

| Поле | Интерпретация |
|---|---|
| byte 2 = 0 | Первый собственный TX sequence устройства |
| byte 3 = 0 | Подтверждает sequence запроса 0 |
| bytes 4–5 | Доступная ёмкость очереди, меняемое поле |
| byte 6 = 2, byte 7 = 1 | Особый локальный BUI-ответ: прошивка пишет TX sequence + 2 и flag 1 |
| bytes 8–9 = `00 3D` | CID ответа BUI |
| byte 10 = 8, byte 11 = 7 | CAN DLC и длина ISO-TP single frame |
| bytes 12–14 = `62 02 20` | Положительный ответ на DID `0220` |
| bytes 15–18 | Четыре компонента версии: `5.9.2.0` |

Байты 19–63 находятся вне CAN-записи. Эмуляция TX builder с заполнителем AA доказала копирование остатка буфера в этот хвост. Декодер его игнорирует. Публичные тестовые фикстуры содержат синтетический хвост; полные локальные отчёты не публикуются автоматически.

[Исследование Bosch eBike HIM](https://de.scribd.com/document/810278403/bosch) связывает DID 544 (`0220`) с чтением версии ПО BUI. Оно описывает старый пакет, но не позволяет считать его sequence постоянной константой. [Официальная страница Bosch](https://www.bosch-ebike.com/en/service/software-update) также перечисляет Intuvia 5.9.2.0; значение на данном устройстве получено непосредственно через USB.

## Контроль таймингов до исправления

Каждый опыт использовал новый HID handle, один handshake и один запрос, затем закрытие; паузы между отдельными опытами превышали несколько секунд. Полный аппаратный reset между ними не подтверждён.

| Заданная задержка | Фактический интервал IN handshake → OUT read, мс | Ответ от начала Write, мс | Итог |
|---:|---:|---:|---|
| 0 | 8.558 | 1.581 | `00 FF` |
| 50 | 68.300 | 1.688 | `00 FF` |
| 300 | 323.245 | 2.017 | `00 FF` |
| 3000 | 3017.528 | 1.439 | `00 FF` |

Гипотеза о том, что только удаление трёхсекундной паузы исправляет старый кадр, не подтвердилась. Точные точки в независимых PowerShell-отчётах — события read_completed/write_call; поле effective_handshake_to_request_ms измерялось раньше фактического Write и не используется для таблицы.

После исправления проведены три положительных чтения в отдельных сеансах: независимый скрипт без заданной паузы, C# runner без паузы и готовый самостоятельный EXE с паузой 3000 мс. Все три вернули `62 02 20 05 09 02 00`. EXE завершился с кодом 0 и `verified_ecu_values=1`; старый тайминг работает с исправленным кадром.

Финальные автоматические проверки: **81 protocol assertions**, **36 session checks**, **20 PCAP assertions**, всего **137 PASS**. Оба Windows x64 EXE опубликованы локально как self-contained single-file .NET 8; фактический USB-тест готового диагностического EXE успешен.

## Windows HID и захват

**VERIFIED ON THIS BIKE:** стандартный Windows HID открывается, Report ID 0, длины IN/OUT 65; драйвер не заменялся. [Microsoft HIDP_CAPS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_caps) включает Report ID в длину API. Точный [исходник HidSharp 2.6.4](https://software.seekye.com/files/oss/hidsharp/HIDSharp264.zip) использует WriteFile и синхронно завершает отменяемое чтение при timeout.

**UNVERIFIED:** фактические транзакции на проводе в этом запуске не захвачены. USBPcapCMD, driver file и service не обнаружены. Установка драйверов не выполнялась. Логи API не названы PCAP; файлы PCAP не имитируются. Сниффер собирается отдельно и требует установленный USBPcap.

## Реализованный объём и ограничения

Windows-программа выполняет один подтверждённый BUI-запрос после каждого handshake. Проверяет весь поддерживаемый заголовок, CID, sequence/ACK, длины, SID и DID; число ECU-значений становится 1 только после положительного ответа. Ошибки USB и сохранения разделены. Все исходные 65/64 байта, UTC-время и Stopwatch-точки сохраняются в JSON.

Нет полноценного общего Sliding Window A, многокадрового ISO-TP, heartbeat, диагностики DU/BMS или гарантии совместимости со всеми Intuvia. Android-ветка оставлена как историческая и всё ещё содержит старое неверное формирование кадра. Эта работа исправляет проверенное Windows-чтение версии BUI.

Автотесты проверяют правильный ответ, старый ошибочный формат, сдвиг записи, stale sequence, другой CID/DID/SID, неверные длины, произвольный хвост, отмену, mutex, таймауты, завершение после ошибки и сохранение отчётов. Они используют fake HID; физические результаты хранятся отдельно.
